## Змоделювати інтернет-магазин гітар у вигляді ER-моделі (Mermaid erDiagram) за попередньо написаним spec.md. Критерії зафіксовані в spec.md: однаковий тип для всіх id і зовнішніх ключів (int), збіг назв зі spec, правильні кардинальності, зв'язок «багато-до-багатьох» лише через змістовну сутність OrderItem.

# Топ-2 розбіжності (spec ↔ артефакт) + коміт-виправлення:

- Діаграма не показувала допустимі значення status, хоча в spec вони були. Виправлено критерієм у spec і перегенерацією діаграми. Коміти: «spec: вимагати відображення значень status у моделі», «model: перегенерувати діаграму зі значеннями status».

- У spec не було зафіксовано рішень (чому stockQuantity у Guitar, чому немає totalAmount, чому OrderItem). Виправлено розділом «Рішення». Коміт: «spec: додати розділ рішень».

# Ключове рішення, які альтернативи зважила і чому обрала цю (ADR):

- Рішення: Order не зберігає totalAmount, суму замовлення обчислюємо з OrderItem (quantity × unitPrice).
- Альтернатива: зберігати totalAmount в Order для зручності й швидкості.
- Чому обрала це: збережена сума дублювала б факт, який уже є в позиціях. Після зміни кількості чи ціни в позиції сума могла б розійтися з реальною, а це порушує 3НФ. Для невеликої моделі зручність не варта ризику суперечливих даних.

# Перевірка, узгодженість із попередньою моделлю (як перевірила):

Для першої роботи попередньої моделі немає, тому я перевіряла узгодженість spec ↔ діаграма. Пройшла по пунктах: назви сутностей і полів, типи (усі id та FK = int, ціни = decimal), ключі (PK у кожної сутності, FK вказують на потрібні сутності), чотири зв'язки проти розділу «Зв'язки» у spec, відсутність дублювання даних. Знайдені розбіжності виправила через зміну spec, а не ручним патчем діаграми.
